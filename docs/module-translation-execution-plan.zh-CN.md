## ReCodeAgent 的借鉴点

ReCodeAgent 使用 Analyzer → Planner → Translator ↔ Validator 流程，通过 Claude Code CLI 执行 Agent。Planner 建立名称映射、目标骨架和自底向上的实施计划，Translator 分文件实现，并根据 Validator 报告修复。

参考实现：`configs/prompt_templates.yaml`、`src/agents/recodeagent/agent.py`、`src/utils/cmd_utils.py`。

采用其明确的阶段交接、名称映射、增量实现和验证反馈循环。将整仓一对一翻译调整为历史模块适配目标工程，优先满足目标已有接口。成功状态由实际编译、测试记录决定，不能仅依据报告文件存在或报告中的 PASS 文本。

## 执行阶段

### 1. 模块任务契约与双端范围

- 新增模块级任务，记录源仓库、revision、项目与模块，以及目标项目、目标基线、需求和允许修改范围。
- 区分源文件归属与目标文件写入范围，补齐现有单仓库迁移执行器的双端映射。
- 保留现有类或函数翻译入口，模块任务使用独立的范围契约。

验收：可创建包含多个源文件和多个目标文件的任务，展示完整范围与外部依赖。

### 2. 模块检索与按需上下文

- 扩展现有检索服务，返回模块摘要、文件清单、公开 API、依赖边与关联测试。
- 首轮输入包含模块结构、依赖信息、目标契约和约束；Agent 通过现有语义查询工具按需读取源码。
- 未解析依赖保留状态，由规划阶段确定后续处理；所有证据绑定明确版本。

验收：可从 SeekDB 选定完整历史模块，并按需获取其源码证据。

### 3. 翻译计划、名称映射和目标骨架

- 基于已有模块划分生成实施计划，明确源类型、接口、文件在目标工程中的位置。
- 为依赖选择复用、替换、适配或一并迁移；明确需要扩大的翻译范围。
- 先确定共享类型和接口，再安排实现顺序，复用现有依赖调度器。
- 循环依赖按联合组处理，确保组内步骤能访问已生成的契约和代码。

验收：跨文件名称、签名和路径一致，循环依赖有可执行的处理安排。

### 4. 模块翻译 Agent 与多文件补丁

- 沿用现有工具调用模型接入，实现 ModulePatchPreparer。
- 一个模块保持统一任务状态，内部按文件或依赖组逐步生成。
- 提供源码查询、目标暂存内容读取、补丁提交与验证工具。
- 宿主将补丁应用到独立暂存环境，后续步骤读取到此前生成的代码；模块生成器返回最终 FilePatch 集合。
- 第一版先完成串行执行，再依据调度器放开独立模块的并发。

验收：从计划自动生成多文件补丁，不需要手工准备 JSON 补丁包。

### 5. 验证、修复与持久化

- 按目标构建、模块测试、受影响项目测试执行验证。
- 有源测试时先确认源侧基线，再迁移相关断言或建立行为对照。
- 将文件、编译诊断和测试结果作为结构化反馈，驱动定向修复。
- 达到执行预算后保留进度与未解决项，恢复时检查基线并重新验证。
- 复用现有运行记录和补丁审阅机制，将任务、映射、验证摘要关联至 SeekDB 中的源与目标版本。
- 回填后重新索引目标版本，更新模块摘要。

验收：失败不显示为成功，中断可恢复，回填后的源码、索引和摘要对应同一版本。

### 6. 界面接入与真实服务验收

- 左侧选择模块，主区域沿用“定义任务 → 选择方案 → 翻译 / 桥接 → 校验与回填”。
- 增加文件范围、依赖处理、执行进度、多文件差异和测试结果视图。
- 使用 code-corpus 中带测试的项目建立隔离目标样例。
- 依次验证单模块多文件、跨模块依赖、编译失败修复和中断恢复。
- 记录模型耗时、工具耗时、token、修复次数和测试结果。

验收：通过真实模型、真实 SeekDB 和真实编译测试完成首个里程碑，不以模拟补丁代替生成链路。

## Code2Code 完整工作流说明

Code2Code 先对目标工程和参考工程分别建库，再执行单次翻译。建库不是一次模型调用，而是按固定顺序完成四层处理。第一步是接入工程：系统登记仓库身份，记录本地目录和工程配置，并捕获不可变的源码快照；每个快照分配唯一的 `revision`，后续所有文件、符号、依赖和模型产物都必须绑定这个版本。第二步是结构解析：`code-indexer` 按文件读取快照，使用对应语言的 Tree-sitter grammar 构建语法树，遍历包或命名空间、类、接口、枚举、结构体、函数、方法、构造函数、字段、参数、类型引用以及 import/export 声明，为每个符号保存名称、限定名称、所属文件、父级符号、签名、源码起止位置和内容哈希；解析不完整的文件保留 `partial` 或 `failed` 状态，不把缺失节点补成猜测事实。第三步是依赖提取：系统从语法树和工程配置中提取导入、继承、接口实现、函数或方法调用、成员访问、字段类型、参数类型、返回类型、模块声明和构建配置等关系，生成带来源位置的依赖边；目标唯一可定位时记为 `resolved`，目标缺失或存在多个候选时保留 `unresolved` 或 `ambiguous`。第四步才是索引建模和发布：结构记录、依赖边、源码片段、诊断和工程元数据先写入 SeekDB 的构建中版本，完成一致性校验后，再生成全文字段和 embedding 向量并发布为可查询版本。查询只能命中已发布的仓库版本，结果可以沿着 `repository → revision → project → file → symbol` 回溯到原始代码。

在上述确定性事实准备好之后，系统才进入 Agent 建模阶段。它的输入不是整个目录的原始文本，而是已经绑定 `revision` 的项目边界、文件角色、符号统计、依赖连通关系、解析诊断和有限的代表性源码片段。Agent 首先判断当前项目或候选范围的整体职责，再结合规模、职责是否单一、依赖边界是否清晰和剩余预算，决定该范围直接作为叶子模块（`stop`），还是拆成若干子范围（`split`）。选择拆分时，系统先校验并保存父节点，再把子范围逐个加入待处理队列；每个子范围由同一个有边界的 planner 再次判断停止或继续拆分，同层互不依赖的范围可以并行。每次判断都会产出模块名称、职责描述、成员文件、依赖摘要、判断依据以及 `stop`、`split` 或预算不足时的 `deferred` 状态。校验通过的节点和父子关系写入版本化模块提案，只有提案完整且与当前 `revision`、文件归属和依赖事实一致时，才投影为 SeekDB 的模块摘要文档和向量。也就是说，Agent 负责解释和组织结构事实，不能改写源码事实；SeekDB 负责保存和发布这些经过绑定、校验的结构与语义投影。在线翻译直接复用已发布的模块、符号和依赖索引，先用模块摘要定位参考候选，再展开到相关文件、符号和必要依赖，不重新对整仓做 Agent 建模。

用户在工作台选择目标模块后，系统会到参考工程的活动 revision 中寻找功能相近的实现。检索不是单一的关键词搜索：SeekDB 同时执行全文召回和向量召回，再用 RRF 融合结果，并结合模块、符号、语言和工程范围做结构过滤。默认开发环境使用确定性的 384 维 hash 向量，正式环境可以换成 OpenAI-compatible 的 embedding 模型；如果更换模型或维度，必须重新建立索引。系统还支持用 DeepSeek 对少量候选做行为语义重排，判断候选是否真的实现了相同职责，而不是只因为类名相似就排在前面。

候选确定后，适配服务不会把参考文件直接复制到目标工程。它先收集目标模块的签名、依赖、调用关系、约束和现有文件内容，同时读取参考实现及其必要上下文。AnalyzerAgent 根据这些材料生成一份分析报告，说明源代码和目标代码之间的对应关系、需要迁移的文件和符号、依赖处理方式以及实施顺序。这份报告是给翻译 Agent 使用的计划和提示，属于建议性结果；真正能否写入目标工程，还要经过宿主和运行时的范围检查。

TranslatorAgent 随后依据目标上下文、参考实现、用户需求和分析报告重新生成目标语言代码。它可以处理多个文件，并按依赖顺序逐步完成接口、共享类型和具体实现。生成结果必须落在事先声明的目标文件和符号范围内，不能擅自改变目标签名、添加越界类型或写入未授权路径。这样做的原因是跨语言迁移通常需要适配接口、异常、配置和依赖，简单文本替换既不能保证语义，也容易破坏目标工程。

生成代码首先在隔离副本中通过目标语言的编译器检查。TypeScript 使用 `tsc`，Python 使用 `py_compile`，Java 使用 `javac`，C# 使用 `dotnet build`，Rust 使用 `rustc` 或 `cargo check`，Go 使用 `go test`。编译器返回的语法、类型、依赖和接口错误会被整理成结构化反馈，最多驱动三轮 repairTranslation 修复。只有最新一轮代码重新编译通过，运行才具备完成条件；模型报告中写着 PASS 并不能代替实际编译结果。

最后，系统把原始文件 hash、生成内容、修改差异、编译结果和未解决事项保存到翻译运行记录中，交给用户审阅。用户确认后才回填目标工程；回填前会再次检查原文件是否仍与开始时一致，避免覆盖用户在翻译期间的修改。回填完成后，目标工程需要重新索引并更新模块摘要。当前这条链路的硬验收标准主要是多文件生成、编译验证、差异审阅、恢复和回滚；行为测试尚未成为所有语言和所有任务的统一完成条件。
