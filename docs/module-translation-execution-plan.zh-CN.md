在 ForeXplore 界面选择功能模块后，完成历史实现检索、跨文件翻译、构建测试、差异审阅和回填，并通过 SeekDB 维护任务状态和目标模块摘要。

## ReCodeAgent 的借鉴点

ReCodeAgent 使用 Analyzer → Planner → Translator ↔ Validator 流程，通过 Claude Code CLI 执行 Agent。Planner 建立名称映射、目标骨架和自底向上的实施计划，Translator 分文件实现，并根据 Validator 报告修复。

参考实现：`configs/prompt_templates.yaml`、`src/agents/recodeagent/agent.py`、`src/utils/cmd_utils.py`。

采用其明确的阶段交接、名称映射、增量实现和验证反馈循环。将整仓一对一翻译调整为历史模块适配目标工程，优先满足目标已有接口。成功状态由实际编译、测试记录决定，不能仅依据报告文件存在或报告中的 PASS 文本。

## 执行阶段

### 1. 模块任务契约与双端范围

- 新增模块级任务，记录源仓库、revision、项目与模块，以及目标项目、目标基线、需求和允许修改范围。
- 区分源文件归属与目标文件写入范围，补齐现有单仓库迁移执行器的双端映射。
- 保留现有类或函数翻译入口，模块任务使用独立的范围契约。

验收：可创建包含多个源文件和多个目标文件的任务，展示完整范围与外部依赖。

### 2. 模块检索与按需上下文

- 扩展现有检索服务，返回模块摘要、文件清单、公开 API、依赖边与关联测试。
- 首轮输入包含模块结构、依赖信息、目标契约和约束；Agent 通过现有语义查询工具按需读取源码。
- 未解析依赖保留状态，由规划阶段确定后续处理；所有证据绑定明确版本。

验收：可从 SeekDB 选定完整历史模块，并按需获取其源码证据。

### 3. 翻译计划、名称映射和目标骨架

- 基于已有模块划分生成实施计划，明确源类型、接口、文件在目标工程中的位置。
- 为依赖选择复用、替换、适配或一并迁移；明确需要扩大的翻译范围。
- 先确定共享类型和接口，再安排实现顺序，复用现有依赖调度器。
- 循环依赖按联合组处理，确保组内步骤能访问已生成的契约和代码。

验收：跨文件名称、签名和路径一致，循环依赖有可执行的处理安排。

### 4. 模块翻译 Agent 与多文件补丁

- 沿用现有工具调用模型接入，实现 ModulePatchPreparer。
- 一个模块保持统一任务状态，内部按文件或依赖组逐步生成。
- 提供源码查询、目标暂存内容读取、补丁提交与验证工具。
- 宿主将补丁应用到独立暂存环境，后续步骤读取到此前生成的代码；模块生成器返回最终 FilePatch 集合。
- 第一版先完成串行执行，再依据调度器放开独立模块的并发。

验收：从计划自动生成多文件补丁，不需要手工准备 JSON 补丁包。

### 5. 验证、修复与持久化

- 按目标构建、模块测试、受影响项目测试执行验证。
- 有源测试时先确认源侧基线，再迁移相关断言或建立行为对照。
- 将文件、编译诊断和测试结果作为结构化反馈，驱动定向修复。
- 达到执行预算后保留进度与未解决项，恢复时检查基线并重新验证。
- 复用现有运行记录和补丁审阅机制，将任务、映射、验证摘要关联至 SeekDB 中的源与目标版本。
- 回填后重新索引目标版本，更新模块摘要。

验收：失败不显示为成功，中断可恢复，回填后的源码、索引和摘要对应同一版本。

### 6. 界面接入与真实服务验收

- 左侧选择模块，主区域沿用“定义任务 → 选择方案 → 翻译 / 桥接 → 校验与回填”。
- 增加文件范围、依赖处理、执行进度、多文件差异和测试结果视图。
- 使用 code-corpus 中带测试的项目建立隔离目标样例。
- 依次验证单模块多文件、跨模块依赖、编译失败修复和中断恢复。
- 记录模型耗时、工具耗时、token、修复次数和测试结果。

验收：通过真实模型、真实 SeekDB 和真实编译测试完成首个里程碑，不以模拟补丁代替生成链路。

## Code2Code 完整工作流说明

我们先分别把目标工程和参考工程建成可查询的版本化资产。工程接入时，系统登记仓库、项目配置和源码位置，并保存一份不可变的源码快照。每份快照都有自己的 `revision`，后面产生的文件、符号、依赖和模型产物都跟着这个版本走，这样用户最后看到的任何候选都能回到当时的原始代码。

有了快照，`code-indexer` 才开始按文件解析源码。它根据扩展名选择对应的 Tree-sitter grammar，遍历包或命名空间、类、接口、枚举、结构体、函数、方法、构造函数、字段、参数、类型引用以及 import/export 声明。每个识别出来的符号都会带上名称、限定名称、签名、父级关系、所属文件、源码范围、内容哈希和解析状态。文件如果只能解析出一部分结构，就保留 `partial` 或 `failed`，不会为了让结果看起来完整而补造缺失的符号。

下一步是把这些结构事实连接起来。不同语言的模块系统、继承语法和工程配置都不一样，所以语言适配工程会在 Tree-sitter 结果上继续处理 Java、C#、TypeScript、Python、Go、Rust、Kotlin、C/C++ 等语言的导入、导出、继承、接口实现、函数调用、成员访问以及字段和类型引用，同时读取 Maven、Gradle、`csproj`、`package.json`、`pyproject.toml` 等配置中的项目引用。这样得到的是统一格式的依赖边和项目依赖图。Java、C# 还可以接入编译器或语言服务来确认更精确的定义、引用和调用关系；JNI、Node-API、KMP 等跨语言关系则必须有明确的注册或桥接证据。任何无法唯一确认的关系都会原样保留为未解析或歧义状态。

这些事实准备好以后，系统先把项目、文件、符号、依赖边、诊断、源码片段、路径、语言、版本和哈希写入 SeekDB，建立按仓库、项目和 `revision` 查询的结构索引。文件和符号也可以在这一阶段生成全文字段和基础向量，供后面的 Agent 查询。这里的 SeekDB 先保存“源码中实际有什么”，还没有替模型决定“这些文件属于哪个业务模块”。

接下来才进入 Agent 建模。Agent 看到的不是整个工程的原始目录，而是已经绑定版本的项目结构、文件角色、符号统计、依赖图、解析诊断和有限的代表性源码片段。它先判断当前范围的整体职责，再根据工程规模、职责是否单一、目录边界和依赖关系决定这里应该直接停在一个叶子模块，还是继续拆分。系统支持“子系统—模块—文件”这样的层级，但不会强迫每个工程都走完三层；小项目可能直接从模块落到文件，大项目才需要先划分子系统。

如果 Agent 认为一个范围还需要细化，系统会先保存父节点，再把子范围交给同一个有边界的 planner 继续判断。彼此没有依赖的子范围可以并行处理，所以大型工程不必等一个分支完全结束后才开始下一个分支。每次判断都会留下模块名称、职责、成员文件、接口、依赖摘要、父子关系和判断依据，并标记这个范围是已经停止、继续拆分，还是因为预算不足暂时待细化。

Agent 的结果不能直接当成事实发布。系统会检查它引用的项目、文件、符号和依赖是否真实存在于当前 `revision`，检查文件有没有重复归属，父子关系是否有效，模块之间有没有非法环路，还会确认 Agent 声称看过的证据确实出现在它收到的上下文中。校验通过后，模块提案和层级关系才会写入版本化产物，并进一步生成模块职责、接口和依赖三个检索视图及其向量。也就是说，工具负责提取事实，Agent 负责解释和组织事实，SeekDB 负责保存和发布经过校验的结果。前端现在看到的目录树，就是这几层结果合在一起的呈现。

模块检索就是在这套离线结果之上寻找可复用实现。用户在目标工程中选中一个模块并输入需求后，系统把目标模块名称、签名、文档说明、核心 API 和需求拼成查询文本。它不会只拿模块名做字符串匹配，而是同时表达“这个模块是谁”“它提供什么接口”和“这次想找什么行为”。检索候选只来自已经登记、拥有活动 `revision` 且分析状态为 `ready` 的参考工程；一次最多查询 32 个参考仓库，返回数量由 `topK` 控制在 1 到 10 个，并受整体时间预算和取消信号约束。

对每个参考工程，系统会在同一个活动版本里查看模块职责摘要、符号和接口信息、源码片段三类视图。全文检索负责命中类名、方法名、领域术语和 API 标识符，向量检索负责找出表述不同但职责相近的内容。两条通道的结果用 RRF 做倒数排名融合：一个文档在某条通道中越靠前，贡献越大；同时被全文和向量召回的文档会得到两边的累加分。结果按照文档 ID 去重，并保留命中的视图、原始分数和版本信息。

召回到的文档还要恢复成真正的模块。模块摘要本身带有模块产物 ID，可以直接定位；符号或源码片段则要依据已审核的文件归属映射回模块，无法可靠归属的命中会被丢弃。之后系统继续检查模块产物是否属于当前仓库和当前 `revision`，`analysisHash`、`planHash`、项目 ID 和模块 ID 是否一致，模块提案是否处于 `ready`，以及模块是否确实包含源文件。过期版本、哈希不匹配或被篡改的提案不会进入候选。

同一个模块可能同时命中职责、接口和依赖三个视图，系统会按“仓库 + 项目 + 模块”把它们合并起来。不同仓库中即使模块同名，也不会被混成一个候选。合并之后，系统用检索相关性和核心 API 匹配度做初排。当前接口名称匹配只做有限归一化，例如忽略参数列表、包路径和下划线差异；它能说明接口形状相近，但不能证明参数类型、异常行为或业务状态完全一致。排序分数大致由 80% 检索相关性和 20% API 名称匹配组成，因此它是候选排序分数，不是功能满足概率。

初排完成后，系统只读取有限的源码证据。候选保留完整文件清单，但通常只预览前 3 个文件，每个文件最多 4,000 个字符，并且明确记录是否截断。这样用户可以快速比较候选的职责、接口、依赖和代表性实现，同时知道这还不是完整的迁移上下文。如果启用了联合重排，系统会把需求、模块说明、核心 API、依赖列表和源码预览一起交给本地 BGE 交叉编码器，在 8 到 20 个候选的小范围内再排一次；它能够判断需求和候选实现是否真正相关，但会增加推理时间，所以是可选步骤，失败或超时也必须显式报告。

最后，系统会再次检查参考工程的活动 `revision` 是否在检索期间发生变化。只有版本仍然一致，候选才会返回前端。返回结果中包含模块名称、来源仓库、来源语言、职责描述、核心 API、完整文件清单、模块依赖、版本化源码预览、匹配和缺失的 API，以及可以回溯到结构事实的证据 ID。用户选定候选后，目标模块、参考模块、必要接口、依赖和源码证据才会交给 Analyzer 和 Translator，进入后面的跨语言翻译和编译验证。

这样，模块检索承担的是“从参考工程找到值得复用的实现”，而不是直接宣布两个模块功能等价。是否能够完成翻译，还要由后续的分析计划、目标工程约束、编译检查和必要的行为验证来决定。
