# 国创分支产品流程与前端展示审查

## 1. 审查结论

当前分支没有需要推倒重做的总体架构错误。项目说明书中的主线“离线建模、在线检索、按需交付”与现有工程接入、模块建模、任务检索、上下文导出和复用迁移能力基本一致。

现阶段最需要解决的不是继续增加功能，而是缩短“技术已经实现”与“评委能够看懂”之间的距离。当前界面把模块解析结果表现成工程诊断文本，模块职责、层次、关键接口和技术效果没有成为主视觉，因此容易给人“输出很多但不知道系统做了什么”的印象。

本轮建议只处理影响比赛叙事和现场演示的主要问题，不按生产系统标准扩展异常分支，也不重构后端算法。

## 2. 以当前处境为前提的审视方式

### 2.1 只检查三类问题

1. 流程是否能从用户输入走到可展示的结果。
2. 界面陈述是否与当前真实实现一致。
3. 评委能否在短时间内识别项目的技术方法和实际产物。

除此之外，低概率错误、完整企业权限体系、复杂恢复流程和极端兼容性不作为当前优先事项。

### 2.2 演示应回答的四个问题

1. 系统读懂了什么工程？
2. 系统如何把代码组织成功能模块？
3. 用户的自然语言任务定位到了哪些实现和依赖？
4. 这些证据如何交给 Agent 继续完成修改或迁移？

只要四个问题能被当前界面连续回答，比赛演示就是成立的。

## 3. 总体流程审查

### 3.1 建议保留的主流程

```text
工程接入与版本快照
  -> 静态解析与依赖证据
  -> 自适应分层模块建模
  -> 全文/向量/多粒度任务检索
  -> 预算内 Context 组织与导出
  -> Agent 修改，或进入复用迁移
  -> 编译检查、差异审阅与回填
```

这条流程与说明书中的两条业务工作流兼容：

- 任务检索可以在 Context 导出处结束，并交给外部 Coding Agent。
- 复用迁移在检索候选之后继续完成分析、翻译、验证和回填。

模块树是工程理解与检索范围，不应被描述成所有任务必须逐层点击的前置步骤。用户既可以直接输入任务，也可以先选择模块缩小范围。

### 3.2 没有发现的严重错误

- 离线建库与在线检索的职责没有颠倒。
- 模块树、依赖关系和向量近邻的语义在说明书中有明确区分。
- 目标工程与参考工程的角色划分成立。
- 编译检查没有被直接宣称为业务行为正确。
- 当前能力和继续增强方向在说明书中已经分列，没有把全部规划伪装成已完成能力。

### 3.3 需要修正的三个主要断点

#### 断点 A：比赛品牌与产品界面名称不一致

说明书统一使用 RECAST，当前主界面仍以 ForeXplore 为主要品牌。代码包名暂时不改没有问题，但比赛演示界面的产品名称应统一，否则截图和答辩材料会像两个项目。

建议：只修改用户可见品牌为 RECAST，并保留“ForeXplore 技术底座”作为必要的内部说明；不进行包名和命令的全仓重命名。

#### 断点 B：模块解析产物被工程诊断淹没

当前 `ModuleWorkspace` 在主操作区下方依次平铺项目名称、状态、摘要、覆盖率、风险、重试按钮、依赖列表、诊断列表和版本信息。大仓或依赖不完整时，负面诊断会成为视觉主体，用户看不到模块划分本身的结果。

建议：把模块成果提升为主内容，把覆盖率、依赖数量和检索状态压缩成结果概览；未解析依赖、诊断和版本统一进入“工程详情”折叠区。

#### 断点 C：任务检索进入迁移时只带入需求文本

当前任务检索页面进入复用迁移时会带入需求，但不会把用户筛选的 Context 或证据选择传入迁移状态。完整后端接通在说明书中也仍标为后续工作。

建议：当前界面使用“带入需求，继续选择参考方案”的准确措辞，不宣称已把检索证据直接送入完整翻译链路。本轮不扩展后端契约，避免为比赛展示制造一个未经验证的大改动。

## 4. 前端改进建议

### 4.1 信息优先级

第一层：用户任务和系统结果。

- 当前工程和索引状态；
- 已识别的顶层范围、模块和叶模块；
- 文件覆盖、依赖证据和检索是否就绪；
- 当前选中模块的职责、关键接口和代码规模。

第二层：技术如何产生结果。

- 静态解析；
- 依赖恢复；
- 分层模块建模；
- 多粒度检索投影。

第三层：工程核查信息。

- 未归属文件；
- 未解析或歧义依赖；
- 解析诊断；
- 仓库、项目和版本标识；
- 重新解析操作。

### 4.2 模块成果区

每个模块只展示真实数据：

- 名称和职责摘要；
- 模块或子系统类型；
- 文件、类型、方法数量；
- 最多若干个核心 API；
- 叶模块、已拆分或待细化状态；
- 模型判断、结构分析或预算限制等判断来源。

不增加虚构准确率、效率提升百分比或业务收益。没有数据时使用明确的缺省文案，不生成看似真实的指标。

### 4.3 技术效果区

技术效果不是再写一段算法介绍，而是将技术与当前工程结果一一对应：

| 技术阶段 | 当前界面证据 |
| --- | --- |
| 静态解析 | 已解析文件及符号数量 |
| 依赖恢复 | 已取得的依赖证据数量与缺口状态 |
| 分层建模 | 顶层范围、模块节点、叶模块、最大深度与待细化数量 |
| 检索投影 | 当前版本是否可进行模块/子系统粒度检索 |

`summary.json` 是内部产物，不适合作为比赛第一层技术阶段名称。它可以保留在工程详情中，但主流程应显示“多粒度检索就绪”等用户可理解的结果。

### 4.4 视觉原则

- 保留当前 VS Code 深色工作台风格，不另做一套展示网页。
- 不增加大面积渐变、玻璃卡片、无意义动效或装饰图标。
- 用分组、字号、间距和有限状态色建立层次。
- 第一屏优先呈现操作和结果，长诊断默认折叠。
- 桌面投屏下必须能读清模块名称、职责和关键数量；窄屏继续保持可滚动和可操作。

## 5. 建议的最小落地范围

### 必须完成

1. 将用户可见主品牌统一为 RECAST。
2. 将项目解析文本块改为“工程理解结果”概览。
3. 展示分层模块、覆盖、依赖证据和检索就绪状态。
4. 选中模块时展示职责、规模、核心 API 和细化依据。
5. 将依赖明细、诊断、版本和重试操作收进工程详情。
6. 将任务检索到迁移的按钮文案改为准确的“带入需求并选择参考方案”。

### 明确不做

1. 不重写模块建模、检索或翻译算法。
2. 不为了界面增加新的后端指标。
3. 不伪造比赛效果数据。
4. 不进行 ForeXplore 包名、命令和历史文件的全仓重命名。
5. 不把所有规划中的跨语言图谱和自动补取描述成已完成。
6. 不新增独立营销站、三维动画或复杂可视化。

## 6. 落地验收标准

1. 打开目标工程或参考工程后，第一眼能看到工程理解结果，而不是诊断长文。
2. 每个已识别模块能显示职责和至少一组真实范围信息；有核心 API 时可直接看到。
3. 技术阶段与当前工程数据对应，不能只是静态宣传词。
4. 所有原有依赖、诊断、版本和重新解析能力仍可从工程详情访问。
5. 任务检索、复用迁移、模块选择和设置入口仍能正常使用。
6. 界面在桌面宽度和窄 VS Code Webview 下均无内容遮挡，关键操作可点击。
7. 页面不新增伪造指标，也不扩大后端能力声明。

## 7. 实施顺序

1. 先调整品牌和文案，消除材料与界面不一致。
2. 重组 `ModuleWorkspace` 的工程结果、模块详情和工程详情。
3. 复用现有数据字段完成技术效果展示，不改协议。
4. 用真实工作台或现有交互数据验证桌面和窄屏。
5. 编译并检查任务检索到复用迁移的完整点击路径。
