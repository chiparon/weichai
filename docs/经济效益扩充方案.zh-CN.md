## 一、现状诊断：为什么现在的 8.8 说服力不足

现有 8.8 节约 900 字，全部为定性表述。按评审视角，存在六个缺口：

| 缺口 | 具体表现 | 后果 |
| --- | --- | --- |
| 无问题基准 | 只说"准备工作占用研发时间"，没有说占用多少 | 读者无法判断收益量级，也就无法判断项目价值 |
| 无测算模型 | 三项效益是并列论断，没有公式、没有代入、没有结果 | 效益不可复算，等同于主张 |
| 未挂钩实测 | 8.7 节已有 235.7 万行建库、287,471 符号、117,420 依赖、136 ms 检索等硬数据，但一条都没进入 8.8 | 已完成的实验投入没有转化为经济论证 |
| 无出处 | 全篇零引用 | 评审无法核验，任何数字都只能当作团队自述 |
| 无成本侧 | 只讲收益不讲投入 | 净收益不成立，"潜力"无法收敛为结论 |
| 无验证方案 | 仅一句"后续企业试用将记录…" | 没有说明标定方法，收益停留为愿望 |

**核心结论**：8.8 需要的不是更多形容词，而是**把第 4–7 章的技术能力和第 8.7 节的实测数据，翻译成一套可复算的效益模型**，并用外部权威数据锚定模型中团队无法自行决定的那部分参数。

## 二、扩充主线：从"定性罗列"改为"可复算的效益模型"

### 2.1 效益传导链

```
技术能力（第 4—7 章） → 研发行为改变 → 可测量指标 → 财务口径收益
```

每一步都必须在文中显式写出，读者才能沿着链条核对。例如：

> 并行混合召回使单次函数级检索从 163 ms 降至 136 ms，且 60 次请求的输出逐次一致（实测）→ 开发者在定位环节的等待与反复搜索减少（行为）→ 定位环节工时下降（指标）→ 按人日折算为研发成本节约（财务）。

### 2.2 四个财务口径

| 口径 | 计量单位 | 适用效益项 |
| --- | --- | --- |
| 人力工时 | 人日 / 人年 → 元 | 定位理解、重复开发、返工修复 |
| 交付周期 | 天 / 周 | 迁移与适配任务的提前交付 |
| 模型与算力 | Token / 元 | Coding Agent 的上下文与探索开销 |
| 资产利用 | 复用次数 / 复用率 | 既有代码资产利用效率 |

### 2.3 三类数据来源必须分开标注

这是本节可信度的关键。所有数字都要标明属于哪一类，避免把文献值当成自己的实验结果：

- **(A) 外部权威基准**：学术论文与官方报告的行业实测值 → 用于设定"问题有多大"
- **(B) 平台实测值**：本项目已有实验记录（第 8.7 节 + `logs/` 原始报告）→ 用于设定"我们能改到多好"
- **(C) 待企业标定值**：只有试点才能得到的系数 → **明确列出并给出标定方法**，而不是假装已经知道

评审对 (C) 的容忍度远高于对"编造数字"的容忍度。主动列出待标定项，是严谨而非心虚。

### 4.1 一条现成但未被使用的论证链：命题文件自己写了损失

命题要求文件在【命题背景】中已经给出了完整的损失链条，而现有 8.8 完全没有引用它。原文措辞可以直接作为效益论证的立论基础：

> "实践中面临的最大挑战是：百万/千万行级仓库的解析和索引效率存在瓶颈以及多语言场景的调用链路还原和逆向困难……传统 LSP 服务、字符串检索、文本匹配等定位方式，无法识别客户端特殊架构带来的隐性代码依赖，依赖链路断裂、检索噪音量大、代码定位不准等问题突出。进而导致 **AI 代码生成准确率低、需求理解偏差、批量改造效率低下**，严重制约大型应用鸿蒙化的高质量迭代与生态开发者高效开发效率。"

这段话里有四个直接可用的经济要素：

| 命题原文表述 | 对应的可量化效益项 |
| --- | --- |
| "解析和索引效率存在瓶颈" | 建库与更新的一次性投入与增量成本（8.8.6 已实测） |
| "调用链路还原和逆向困难" | 依赖恢复工时与返工（8.8.5） |
| "依赖链路断裂、检索噪音量大、代码定位不准" | 定位与理解工时（8.8.2、8.8.3） |
| "AI 代码生成准确率低、需求理解偏差、批量改造效率低下" | Agent 上下文成本与迁移周期（8.8.4、8.8.5） |

**建议做法**：在 8.8.1 开头用一句话把命题背景的这组损失表述接过来，然后说明"本节将这组定性损失逐项折算为可复算的量化指标"。这样效益论证的出发点就不是团队自我主张，而是**命题方自己认定存在的问题**，评审的接受成本最低。

此外，命题文件给出了上下文容量的换算基准（"256K 上下文仅可覆盖约 2 万行代码"），这一条应直接引用，用于第 5.1 节第 4 条的失配倍数计算。

### 5.1 可直接写进正文的派生结论

由已有实测值与命题给定条件，可以立即算出四条结论，不需要新实验：

1. **建库成本可预测且很低**：2,038 s ÷ 2.3567 百万行 = **865 s/百万行 ≈ 14.4 分钟/百万行**。按线性折算，千万行工程全量建库约 **8,648 s ≈ 2.4 小时**，且为一次性投入，后续由增量更新摊薄。
2. **检索时延不是瓶颈**：实测 136 ms 对命题 10 s 上限有约 73 倍余量，说明未来可以在不牺牲时延的前提下继续扩大仓库规模或提高召回通道数量。
3. **在线查询的边际模型成本接近零**：在线检索走本地索引与 384 维小模型，不调用大模型；大模型只参与离线模块职责分析（7,702 个文件仅消耗 24 次请求）。这与"每个开发任务都让 Coding Agent 重新逐文件探索"的成本结构有本质区别。
4. **上下文容量与工程规模存在数量级失配**：按命题给出的换算关系，256K 上下文约覆盖 2 万行代码。命题描述的单模块规模为十万行，即单模块已达单次上下文容量的 **5 倍**；全工程百万至千万行，则是单次上下文容量的 **50–500 倍**。

   > 这一条是整个经济效益论证的**起点**：如果上下文容量与工程规模处于同一数量级，那么"把整个工程塞进提示词"就是可行方案，RECAST 的价值无从谈起。正因为存在 50–500 倍的失配，**"如何从工程中筛出该看的那一小部分"才成为不可回避的成本项**，而 RECAST 正是把这项成本从"每个任务重复支付"变成"建库时一次性支付"。

   **可写成计算公式的形式**：

   ```
   失配倍数 = 工程规模（行） ÷ 单次上下文可覆盖行数
   单模块： 100,000  ÷ 20,000 ≈ 5 倍
   全工程： 1,000,000 ～ 10,000,000 ÷ 20,000 ≈ 50 ～ 500 倍
   ```

   把"失配倍数"作为效益论证的入口，比直接说"上下文窗口有限"更有力，因为它是**可计算、可核对**的，且换算基准来自命题文件本身而非团队自述。

## 六、量化测算模型与情景分析

### 6.1 参照情景的定义

为避免数字悬空，先定义一个**可线性缩放的单位情景**，读者可按自身规模换算：

- 每 **1,000 名**参与大型工程维护、复用与迁移的研发人员；
- 人均年有效研发工时 **D = 220 人日**；
- 价值换算采用命题企业公开口径：华为 2025 年研发费用 **1,923 亿元** ÷ 研发员工约 **11.4 万人** = **168.7 万元 / 人·年**（全口径研发投入折算，含设备、云与管理分摊）。

> **口径说明（务必写入正文）**：168.7 万元/人·年 是"研发投入口径"而非"人力薪酬口径"，代表工程工时的全部机会成本，因此是价值换算的**上限**。若仅按人力薪酬口径（软件研发人员综合用人成本约 40–60 万元/人·年）折算，同一工时节省对应的金额约为表中的 1/3–1/4。建议正文同时给出两个口径，取低者作为结论。

### 6.2 模型一：代码定位与理解工时

```
ΔH₁ = N × D × α × β
```

| 符号 | 含义 | 取值来源 |
| --- | --- | --- |
| N | 参与大型工程维护/复用/迁移的研发人数 | (C) 企业实际 |
| D | 人均年有效研发工时（人日） | (A) 通用假设 220 |
| α | 代码定位、阅读与依赖梳理占研发工时比例 | (A) 文献基准，两条推导路径见下 |
| β | RECAST 可压缩该环节的比例 | (C) 试点标定，文献给出参考区间 |

**α 的两条推导路径（建议正文同时给出，取保守值）**：

| 路径 | 依据 | 得出的 α 量级 |
| --- | --- | --- |
| 路径一：维护工作构成 | 维护工作量中完善性约 56%、适应性约 23%（合计约 79%），两者均以**读懂既有代码**为前提；纠错性仅约 21%（Lientz, Swanson & Tompkins, CACM 21(6):466–471, 1978, DOI: 10.1145/359511.359522） | 在维护类任务中，代码理解相关工时占比可达 **50% 以上** |
| 路径二：程序理解时间占比的现场实证 | Xia et al., *Measuring Program Comprehension: A Large-Scale Field Study with Professionals*, IEEE TSE, DOI: 10.1109/TSE.2017.2734091；Roehm et al., *How Do Professional Developers Comprehend Software?*, ICSE 2012；Minelli, Mocci & Lanza, *I Know What You Did Last Summer*, ICPC 2015 | 需按原文数值确定，**本次未逐字核验** |

> 下文的敏感性分析采用 **α = 20%/25%/30%** 三档，**已显著低于路径一推出的量级**。这是刻意的保守处理：路径一的 79% 是"维护工作量内部"的构成，而模型中的 α 是"全部研发工时"中的占比，二者口径不同，直接代入会高估。正式测算时 α 应按企业实际任务结构重新标定。

**每 1,000 名研发人员的敏感性表**（按 168.7 万元/人·年 折算）：

| α \ β | β = 10% | β = 20% | β = 30% |
| --- | --- | --- | --- |
| α = 20% | 4,400 人日 ≈ 20 人年（3,374 万元） | 8,800 人日 ≈ 40 人年（6,747 万元） | 13,200 人日 ≈ 60 人年（10,121 万元） |
| α = 25% | 5,500 人日 ≈ 25 人年（4,217 万元） | 11,000 人日 ≈ 50 人年（8,434 万元） | 16,500 人日 ≈ 75 人年（12,651 万元） |
| α = 30% | 6,600 人日 ≈ 30 人年（5,061 万元） | 13,200 人日 ≈ 60 人年（10,121 万元） | 19,800 人日 ≈ 90 人年（15,182 万元） |

> **人力成本口径的下限**：上表按全口径研发投入折算（168.7 万元/人·年）。若改用人力薪酬口径（F-3：IT 行业城镇非私营单位年均工资近 25 万元），同一工时节省对应的金额约为上表的 **1/6 到 1/7**。建议正文同时给出两个口径，并以人力薪酬口径作为结论——**保守的结论比漂亮的结论更耐追问**。

### 6.3 模型二：避免重复开发

```
ΔH₂ = F × p × γ × W × (1 − ρ)
```

| 符号 | 含义 | 取值来源 |
| --- | --- | --- |
| F | 年新增/改造功能模块数 | (C) 企业实际 |
| p | 与既有实现存在功能重叠的比例 | (A) 文献重复代码/功能重叠基准 |
| γ | 其中可被检索识别并转为复用的比例 | (C) 试点标定 |
| W | 单功能模块平均实现投入（人日） | (C) 企业实际 |
| ρ | 复用后仍需适配的残余工作量比例 | (C) 试点标定 |

**p 的取值注意**：文献基准（D-3）给出的是"GitHub 上约 70% 的代码存在重复"，这是**开源生态的实测值**，不能直接等同企业内部重复率。企业内部重复率受架构治理、代码评审和平台化程度影响，通常低于开源生态。因此：

- **不要**直接把 70% 代入 p；
- 建议的做法是**在本项目目标代码库上实测**克隆群数量、同源分叉比例与重复行占比，用自测值作为 p，并引用 D-3 说明"重复是软件工程的普遍现象，公开生态中可达约 70%"。自测数据的可核验性最强，也最能体现团队工程能力。
- 论证的写法应当是"**缺乏全局资产检索与同源追踪能力，导致克隆分叉后不一致演变**"（依据 D-4），而不是"重复代码导致缺陷"——后者不符合实证结论，且与本项目的技术价值无关。

**γ 与 ρ 的参考上界**：D-6 给出的复用收益（NASA SEL 研发成本下降 55%，Boeing STS 返工下降 31%）可作为 $\gamma$ 与 $\rho$ 组合效果的乐观上界参考，实际取值仍须由试点标定。

### 6.4 模型三：Coding Agent 的上下文与探索成本

```
ΔC₃ = T × (C₀ − C₁) + ΔH₃
```

| 符号 | 含义 | 取值来源 |
| --- | --- | --- |
| T | 年需跨文件理解的 AI 编码任务数 | (C) 企业实际 |

此模型的价值在于：**它同时给出正向收益（Token 与轮次下降）和成本侧（平台调用成本≈0）**，因此净收益恒为正，只需标定幅度。

METR 实验的关键变量正是"**在自己熟悉的超大型代码仓库中工作**"，与本项目"百万至千万行级工业软件代码迁移"高度同构。这直接给出本项目的立项理由：

> **AI 提效不是自动发生的。在代码库规模超出上下文窗口、开发者依赖大量隐性工程上下文时，通用 AI 助手的净效应为负。工程上下文的供给能力，是决定 AI 提效为正还是为负的关键变量。**

> ⚠️ **必须标注为论证性推演，不是实测结果**。同时在说明书中应当**成对引用** 55.8% 与 −19%——只引积极数据会被评审直接击穿，而把 −19% 转化为立项理由反而最能体现团队对产业现实的判断力。

### 7.5 建议在正文中采用的"三句话"论述

若篇幅受限，至少要保住以下三条论述——它们是整节效益论证的骨架：

1. **失配是起点**：按命题给出的换算，256K 上下文约覆盖 2 万行代码，而命题描述的工程规模是它的 50–500 倍。工程级筛选因此是每个任务都必须支付的固定成本，RECAST 把它变成一次性投入。
2. **检索质量是关键变量**：METR（2025）在 16 名资深开发者、246 个真实任务的随机对照实验中发现，在开发者自己熟悉的大型代码库中，AI 工具使完成时间**增加 19%**，而开发者主观仍认为快了 20%。这说明工程上下文供给是决定 AI 提效正负的变量，也是本项目效益的来源。
3. **成本侧已经实测，收益侧给出标定路径**：建库 14.4 分钟/百万行、单机内存峰值 1.386 GiB、在线查询不调用大模型——投入是可测算且可控的；收益系数则通过同任务、同模型的 A/B 对照标定，不预先假定有利取值。

```latex
\subsection{降低代码定位与理解成本}

大型软件系统的维护投入并不主要用于修复缺陷。对应用软件维护构成的经典实测显示，完善性维护约占 56\%，适应性维护约占 23\%，纠错性维护仅约占 21\%\textsuperscript{[1]}。前两类合计约 79\%，都以读懂既有代码、确认依赖范围为前提。另一组来自搜索引擎企业内部的实证研究进一步表明，代码检索是开发者的高频日常活动，其动因之一正是寻找可复用的既有实现；十年后的复现研究发现这一需求依然存在\textsuperscript{[2]}。因此，代码定位与理解是维护成本的主要构成，而不是附带开销。

RECAST 对这一环节的作用可以直接用同一语料、同一查询的前后对照衡量。在 VS Code 主工程（7,702 个文件）上，构建"定位相关实现并补齐依赖上下文"的完整任务查询，单次耗时由约 19 至 20 秒降至 4.955 秒，返回 10 条结果、17 条源码证据，覆盖 4 个文件、260 行源码，所需方法未被截断，上下文为 7,813 个 token。在同一批 Java 与 TypeScript 函数级任务上，12 项任务各重复 5 次、共 60 次请求，包含检索、源码读取与上下文构建的平均响应时间为 136 毫秒；改用并行混合召回后由 163 毫秒降至 136 毫秒，且 60 对输出内容逐次核对一致。命题要求平均检索时间控制在 10 秒以内，实测结果保留了约两个数量级的余量。

\subsection{提升代码资产复用率，减少重复开发}

企业长期积累的业务实现分散在不同仓库、模块和技术栈中，已有功能难以被及时发现。公开生态的实测显示，代码重复是软件工程的普遍现象：对 GitHub 全量代码的分析发现约 70\% 的代码存在重复\textsuperscript{[4]}。更值得关注的是重复的后果而非重复本身——多项实证研究的一致结论是，克隆代码未必更易出错，真正的风险集中在"本应同步却已经分叉"的克隆\textsuperscript{[5]}。这一结论恰好指向本项目的价值：企业缺少的不是"禁止拷贝"的规范，而是\textbf{全局资产检索与同源追踪能力}。

RECAST 的跨仓库复用检索实验直接检验了这一能力。在由 13 个无关仓库与 3 个功能等价实现（C\#、Python、TypeScript）构成的混合语料中，对 102 个目标类进行功能等价检索：一阶段召回率为 97.06\%，最终 Top-4 召回率为 94.12\%，Top-4 命中率为 97.06\%；后续翻译与编译验证的编译通过率为 91.18\%。该结果表明，系统能够在包含大量干扰仓库的真实混合语料中，以可接受的候选数量定位到功能等价的既有实现，直接对应命题对检索准确率不低于 90\% 的要求。

复用带来的收益已有工业实证：美国国防部公开文件汇总的案例显示，NASA 软件工程实验室报告研发成本下降 55\%，Boeing 报告返工下降 31\%、投资回报率 7.75:1\textsuperscript{[6]}。这些数字来自不同组织与不同项目类型，只能作为量级参考，不能直接套用于本项目的预测。工时测算因此采用如下形式：

\begin{equation}
\Delta H_2 = F \times p \times \gamma \times W \times (1 - \rho)
\end{equation}

其中 $F$ 为年新增或改造的功能模块数，$p$ 为与既有实现存在功能重叠的比例，$\gamma$ 为其中可被检索识别并转为复用的比例，$W$ 为单功能模块的平均实现投入，$\rho$ 为复用后仍需适配的残余工作量比例。$p$ 不直接采用公开生态的重复率，而是在目标代码库上实测克隆群数量、同源分叉比例与重复行占比后确定；$\gamma$ 与 $\rho$ 由试点标定。

\subsection{降低 AI Coding 的上下文与探索成本}

把完整工程纳入模型上下文并不可行，且"窗口更大"并不等于"更会使用上下文"。多项评测给出了一致的结论：关键信息位于上下文中部时，多文档问答准确率下降约 20 个百分点，并且扩展上下文版本并不优于其短上下文同门模型\textsuperscript{[7]}；模型的有效上下文长度普遍远低于其宣称长度\textsuperscript{[8]}；在移除字面匹配、必须依赖语义关联的设定下，多数模型在 32K 长度时跌至其短上下文基线的 50\% 以下\textsuperscript{[9]}。真实代码检索正是需求描述与实现代码之间没有字面重叠的语义匹配，退化只会更严重。

更关键的是，在大型代码库中，通用 AI 助手的净效应可能是负的。一项随机对照实验以 16 名资深开发者为对象，让他们在自己长期维护、熟悉的大型开源仓库中完成 246 个真实任务：使用 AI 工具后任务完成时间增加 19\%，而同一批开发者事前预测会快 24\%、事后仍主观认为快了约 20\%，预期与现实之间存在约 40 个百分点的落差\textsuperscript{[10]}。该实验的工作场景与大型工业软件迁移高度相似。这说明 AI 提效并非自动发生，工程上下文的供给能力是决定其正负的关键变量。

RECAST 在成本侧的处理方式与逐任务探索不同。系统按 token、文件数和源码行数三个维度对最终返回文本施加约束，用 cl100k\_base 对实际导出文本重新计量，按仓库、版本、路径与内容哈希识别重复片段并合并相互包含的源码范围。大模型只参与离线的模块职责分析：在 7,702 个文件的主工程上仅消耗 24 次模型请求，即形成 66 个模块与 6 个子系统；在线检索使用本地索引与 384 维语义编码模型，不调用大模型。由此，平台的模型成本集中在建库阶段并可被后续全部任务分摊，在线查询的边际模型成本接近于零。作为对照，开放式智能体方案在仓库级修复任务上的公开成本约为每实例 0.34 美元\textsuperscript{[11]}，而图引导的定位方案报告成本降低约 86\%\textsuperscript{[12]}，说明结构化定位对成本的影响可达数量级。

Agent 上下文成本的测算形式为：

\begin{equation}
\Delta C_3 = T \times (C_0 - C_1) + \Delta H_3
\end{equation}

其中 $T$ 为年需跨文件理解的 AI 编码任务数，$C_0$ 与 $C_1$ 分别为未接入与接入平台时单任务的模型调用与检索成本，$\Delta H_3$ 为因依赖遗漏导致的返工与人工补查工时。$C_0$ 与 $C_1$ 由试点 A/B 对照的 token 计量与模型定价直接换算，不依赖估算。

上述成本结构的差异可以用公开的同基准对照说明。在同一条仓库级修复基准上，开放式智能体方案的单实例成本约为 4.01 美元，而先结构化定位、再一次性生成的三阶段流水线约为 0.34 美元\textsuperscript{[11][17]}，两者相差约一个数量级。定位环节本身并不廉价：对定位类智能体轨迹的统计显示，单条轨迹的 token 消耗中位数约为 2.86 万\textsuperscript{[18]}。这说明"找代码"的开销足以影响整个任务的经济性；把它从每个任务中剥离出来、交由确定性索引完成，改变的不是速度，而是成本结构。

在组织层面，提效同样不会自动发生。行业调研的回归分析显示，AI 采用率每提高 25\%，交付吞吐量下降 1.5\%、交付稳定性下降 7.2\%\textsuperscript{[19]}，与前述个体层面的实验结果方向一致。两项研究共同指向同一结论：AI 工具的价值取决于工程上下文与研发流程的配套程度，而不是工具本身的先进程度。这也解释了为什么本项目的定位是工程上下文供给层，而不是又一个编码助手。

\subsection{缩短大型迁移与适配周期}

迁移与适配是本项目效益中最直接可观察的一项。命题面向的鸿蒙化场景具有明确的工作量特征：公开披露的信息显示，微信为适配鸿蒙成立了约 800 人的团队，约占其开发人员的一半\textsuperscript{[13]}；《鸿蒙生态人才白皮书 2025》测算未来三至五年鸿蒙生态新增人才需求将超过 100 万人\textsuperscript{[14]}。与之相对，原生鸿蒙终端设备已超过 6,600 万台，注册开发者超过 1,100 万\textsuperscript{[15]}。迁移侧的工作量无法仅靠增加人力解决，工程化提效因此从可选项变为必要项。

迁移的难点集中在依赖恢复而非语法转换。跨语言依赖无法由通用文本匹配或单一语言的语义分析完整恢复：专门的跨语言指针分析工作通过结构化的跨语言分析，对 JNI 方法调用与对象创建的解析召回率达到 97.7\% 与 96.9\%\textsuperscript{[16]}，这一水平需要专门的分析能力才能达到。RECAST 已接入明确 JNI 导出、N-API 注册链以及同模块 KMP 声明与实现的匹配规则，在 VS Code 工程中提取了 117,420 条导入、导出及工程引用关系；修改 N-API 注册信息后，增量分析能够更新相关调用关系，结果与相同源码的全量构建一致。对于缺少注册、模块不匹配或存在多个候选目标的情况，系统保留未解析或歧义状态，不生成不可靠的连接。

迁移效益的测算形式为：

\begin{equation}
\Delta V_4 = M \times L \times \tau \times v
\end{equation}

其中 $M$ 为年迁移模块或应用数，$L$ 为单模块平均投入（人月），$\tau$ 为周期压缩比例，$v$ 为人月成本。$M$ 与 $L$ 取自企业实际任务，$\tau$ 由迁移任务的试点对照标定。除直接的人力节省外，迁移周期缩短还带来业务上线提前的间接收益，该部分在试点中按业务口径单独评估，不计入本节的人力工时测算。
```

### 8.8.7 测算验证方案与不确定性说明（完整草稿）

```latex
\subsection{测算验证方案与不确定性说明}

本节给出的效益模型包含若干只能由企业试点确定的系数。为避免把待标定参数当作已知结论，团队将其单独列出，并给出对应的标定实验设计。

标定采用同任务、同模型、同硬件条件下的 A/B 对照。对照组使用通用检索与逐文件探索方式，实验组接入 RECAST 的任务检索与上下文构建接口；两组使用相同的自然语言任务集、相同的目标工程快照和相同的代码生成模型，仅改变工程上下文的获取方式。每项任务记录代码定位与分析工时、检索命中情况、Agent 交互轮数、输入与输出 token 数、编译与行为测试结果，以及人工修复的代码行数与工时。

待标定系数与验证方式对应如下：压缩比例 $\beta$、可识别复用比例 $\gamma$ 与残余适配比例 $\rho$、周期压缩比 $\tau$ 由上述 A/B 对照直接测得；单任务模型成本 $C_0$ 与 $C_1$ 由 token 计量与模型定价直接换算。所有系数给出置信区间与样本量，而不是单一取值。
```

## 九、风险与免责表述建议

扩充经济效益章节最大的风险不是数字太小，而是**数字来源不清**。以下八条建议用于保护论证的可信度：

| 风险 | 表现 | 建议做法 |
| --- | --- | --- |
| 把文献值说成自己的结果 | "我们使效率提升 55.8%" | 文献值只能用于刻画**基线损失**，平台能力必须用平台实测值表述 |
| 跨语料直接比较 | 用 4.96 s（VS Code 大仓）与 136 ms（Java/TS 小语料）作直接对比 | 同一查询同语料的前后对照（19–20 s → 4.955 s）才是可用证据；跨语料比较须加限定语 |
| 用全口径数字当人力成本 | 直接写"节约 8,434 万元" | 同时给出人力薪酬口径，取低者作为结论；全口径仅作上限说明 |
| 忽略成本侧 | 只讲收益 | 必须包含 8.8.6；本项目的成本侧恰好是强项，不写等于浪费 |
| 单点估计 | 给出一个确定的总收益 | 用保守/中性/积极三档 + 敏感性表，并说明标定方法 |
| 引用不可溯源的数据 | 引用"IBM 缺陷修复成本 1:100""技术债占研发投入 40%""据 ISO/IEC 14764 维护占 60–80%"等 | 这四条**已被溯源考证判定为无法核实或误引**，一律不用；替代方案见 7.3 节 D 小节 |
| 只引积极数据 | 只写"AI 提效 55.8%"，回避 METR 的 −19% | 必须成对引用，并把 −19% 转化为本项目的立项理由（见 7.3 节 E 小节） |
| 混淆统计口径 | 用"鸿蒙生态设备 13 亿台"作为迁移需求基数 | 必须使用**原生鸿蒙终端 6,600 万台**；生态设备口径含 IoT，两者相差约 20 倍 |

**一句话原则**：8.8 的目标不是让评审相信"这个项目能赚很多钱"，而是让评审相信"**这个团队知道钱从哪里来、怎么算、以及哪些还没算准**"。后者才是产业赛道真正考察的能力。

### 9.1 建议在说明书正文中显式加入的一段声明

在 8.8 末尾（或 8.8.1 内）加入下面这段，成本极低、收益极高：

> 本节数据分为三类：外部权威基准、平台实测值与待企业标定值。外部基准用于刻画行业现状，平台实测值用于刻画系统当前能力，待标定值均已列出标定方法。团队在数据整理过程中剔除了若干流传广泛但无法溯源的说法（例如缺陷修复成本的固定倍数、维护成本占全生命周期的固定比例区间），以避免以未经核实的数字支撑结论。所有平台实测数据均可在项目日志中复现。

这段话的作用是**主动划定能力边界**。产业赛道的评审通常来自企业，他们判断一个学生团队是否可信，往往不看他声称做到了多少，而看**他是否知道自己没做到什么**。
